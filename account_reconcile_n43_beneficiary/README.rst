Resolve outgoing N43 beneficiaries against Odoo 19 partner mapping
models without selecting suppliers by invoice numbers. Preserve the
structured N43 records and avoid any automatic reconciliation.

Readable label and partner criteria support Starts with, Contains, Ends
with, Exactly equals and advanced Python regular expressions. Plain text
is stored with its options, rather than as a generated expression.
Existing native conditions and mappings remain available. Ambiguous
applicable mappings do not choose a partner by sequence.

Configuration
=============

1.  Install OCA **account_reconcile_oca** and the N43 importer for 19.0.
    Enable **Resolve N43 Beneficiary** in the bank journal and keep N43
    partner search at **None** for the priority scenario. Add only
    actual additional holders.

2.  Check an original bank file. Complementary record ``2305``
    (selection ``05``) is the expected CajaMar layout and still needs
    validation against the real file.

3.  In the native reconciliation model, create EXACTLY ONE counterpart
    line with the target **Partner** and NO account. Odoo computes
    ``mapped_partner_id``. Keep the trigger **Manual** unless automation
    has separately been authorized.

4.  Under **Readable Matching > Partner Identification**, select a match
    type, enter literal text and choose case sensitivity. Examples:

    =========== =============== ============== =====================
    Match type  Text            Case-sensitive Counterpart partner
    =========== =============== ============== =====================
    Starts with COREMUTUA       No             Mutua Madrileña
    Contains    TEMPLAGLASS     No             Templaglass S.L.
    Contains    VIDRIOS SALINAS No             Vidrios Salinas, S.L.
    Contains    VBH             No             VBH Iberia, S.L.
    =========== =============== ============== =====================

5.  Use **Bank Label Condition** for an additional condition on the
    COMPLETE bank label, independently of identifying the beneficiary.
    Restrict journal, partners and signed amount through the native
    fields when appropriate.

6.  N43 supplier matching uses the extracted beneficiary name, excluding
    the holder and invoice reference. Ordinary CORE matching uses the
    full label. Distinct applicable partners are ambiguous: no partner
    is chosen by sequence.

7.  Plain text is literal, including ``%``, ``_``, brackets and dots.
    Starts with is anchored; Contains is not; Exactly equals does not
    accept extra characters. Advanced **Python** regex uses
    ``re.match``, with its original flags. Python expressions are not
    sent to PostgreSQL. Native advanced conditions remain available and
    are checked in Python AND PostgreSQL, because native OCA SQL
    executes them with ``~*``. Their engine and search semantics differ.

8.  On upgrading the first 19.0 addon release, its existing native
    partner mappings retain their previous Python search/IGNORECASE or
    casefold behavior. No trigger is changed. **Simplify Recognized
    Prefix Rule** converts only literal anchored prefixes that can be
    represented without losing meaning. Other expressions remain
    advanced, with their original definition retained.

9.  For migration FROM 18.0, read ``MIGRATION_ES.md`` before running
    OpenUpgrade. The addon recovers original scopes/restrictions from
    snapshots and the migration's legacy mapping link. It cannot fix an
    exception during account's earlier migration phase. Original
    mappings/models are not deleted.

10. Historical imports require explicit legacy opt-in and a verified
    extraction pattern. The addon identifies partners; Odoo/OCA still
    control selection of outstanding payments and reconciliation.

Usage
=====

Import an N43 file. For enabled bank journals, the beneficiary
complementary record is preserved independently and matched to a unique
Odoo 19 mapping model. A valid non-holder partner is never replaced.

Resolution happens before statement-line creation because the OCA
importer sets skip_retrieve_partner in its creation context. Re-running
partner retrieval on existing lines is also supported, with the
journal's optional legacy extraction configuration for unmarked
historical data.

Unrecognized or conflicting beneficiaries are left unassigned for manual
review. No invoice, payment or bank reconciliation is created by this
addon.

See the `migration
guide <https://github.com/zurbaran/odoo_metal_manufacturing/blob/19.0/account_reconcile_n43_beneficiary/MIGRATION_ES.md>`__
and `validation
report <https://github.com/zurbaran/odoo_metal_manufacturing/blob/19.0/account_reconcile_n43_beneficiary/VALIDATION.md>`__
before rollout.

Known issues / Roadmap
======================

Validate complementary record 2305 with an original CajaMar N43 and
complete a real pending-payment reconciliation on a database copy before
production rollout. The regression suite uses controlled bank fixtures
and posted payment items.

Date equality, payment candidate scoring and automatic reconciliation
policy are outside partner identification. This addon does not implement
them.
